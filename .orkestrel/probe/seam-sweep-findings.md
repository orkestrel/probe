## [HIGH] (concurrency) The runtime deadline is armed before the inspection is queued, so one claim's timeout destroys another claim's proof

`src/server/Probe.ts:181`

**What goes wrong.** `#inspectRuntime` arms its deadline at line 181, one line BEFORE `stage.inspect(subject)` at line 184 appends the inspection to `RuntimeStage.#tail`. The deadline therefore measures queue time plus execution time, not "one runtime stage" as `ProbeOptions.deadline` declares (src/core/types.ts:273-274). Two overlapping `prove` calls are reachable: `bindServer` hands each inbound message to an `async` listener without awaiting the previous one (node_modules/@orkestrel/mcp/dist/src/core/index.js:1375), `createProbeServer` calls `probe.prove(input)` straight from the tool (src/server/factories.ts:35), and `Probe.prove` (Probe.ts:86) has no mutual exclusion. Timeline with the default 30 s deadline: prove(A) and prove(B) both start at t=0, so the runtime tail holds [A.case, B.case]. A.case runs 20 s. At t=20 s A.case resolves and A.control enqueues, capturing `stage = this.#runtime` at line 179. B.case only now begins running, but B's timer has been armed since t=0, so at t=30 s it fires with B.case barely started. `#inspectRuntime` then emits `expire` for claim B (line 189) — an event documented as "the coordinator's deadline fired and the runtime worker was recycled" (src/core/types.ts:245-246) — and awaits `#recycle(stage)` (line 190), which calls `stage.destroy()` and installs a replacement at line 215. A.control is already bound to the destroyed instance, so when it dequeues, `RuntimeStage.#inspect` throws `'The runtime stage has been destroyed'` (RuntimeStage.ts:124) and prove(A) rejects with an internal error after its case ran clean. Nothing hung: a healthy resident Vitest was torn down and rebuilt, and an unrelated claim was failed. The same shared field bites a second way — `#recycle` awaits `stage.destroy()` for up to `#deadline` ms before line 215 replaces `#runtime`, and every `prove` entering line 179 during that window captures the already-destroyed stage and fails immediately at RuntimeStage.ts:61.

**Evidence.** Probe.ts:179-181 `const stage = this.#runtime` / `const timeout = createTimeout({ ms: this.#deadline })` / `timeout.start()` — then line 184 `stage.inspect(subject)`. RuntimeStage.ts:62 `const inspection = this.#tail.then(() => this.#inspect(subject))` is the queue the armed timer is now racing. `@orkestrel/timeout` documents `start()` as arming the deadline immediately (node_modules/@orkestrel/timeout/dist/src/core/index.d.ts:78-80), so no part of the budget is deferred to dequeue. Probe.ts:214-215 `if (this.#destroyed || this.#runtime !== stage) return` / `this.#runtime = new RuntimeStage(this.#workspace)` — the swap is guarded against double-replacement but nothing rebinds an inspection already queued on the old stage. RuntimeStage.ts:124 `if (this.#destroyed) throw new Error('The runtime stage has been destroyed')` is where A's control dies.

## [HIGH] (contract-coverage) The type stage cannot resolve a candidate file that is not already on disk, so `Source.path` "need not exist" is false and no receipt can be issued for a new file

`src/server/stages/TypeStage.ts:184`

**What goes wrong.** The `Source` contract states twice that a path "need not exist on disk" and that "the type and lint stages read the text from memory" (src/core/types.ts:25-31, src/core/shapers.ts:18). `TypeStage` honours that only for `readFile` and `getScriptSnapshot`. Its `LanguageServiceHost` passes `fileExists`, `directoryExists`, `readDirectory`, and `getDirectories` straight through to `typescript.sys`, and TypeScript's module resolution consults `fileExists`, not `getScriptFileNames`. So when `case.test` imports a `case.files` entry that is not yet on disk — the package's whole purpose, proving a file an agent just wrote — the test's semantic diagnostics carry a spurious TS2307 "Cannot find module". That finding lands in `checks`, `computeReceipt` (src/core/helpers.ts:99) then fails its `clean` condition, and `Verdict.receipt` is never issued. The defect is invisible to the boot control because `#arm` writes its dependency to disk with `writeFileSync` (src/server/Probe.ts:140) before inspecting, so the only case the package exercises itself with is the one case that escapes.

because it makes the repair cheaper — a distinguishable state exists, so the fix does not need to
